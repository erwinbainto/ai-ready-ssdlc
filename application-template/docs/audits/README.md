# Audits & Verification Evidence

This folder holds verification artifacts, audit reports, and findings from review processes — evidence of what was examined, by whom, and what was discovered.

---

## Contents

### Audit Reports & Findings

Generated by specialist review agents:
- **Adversarial reports** — Security audits, code reviews, design critiques, threat models
- **Verification traces** — Build outputs, test suite runs, lint/checkstyle results
- **Evidence vault** — Refusal captures, session traces, cost/latency reports, baselines

### Report Structure

Each audit report captures:
- **Observation:** What was examined and when
- **Evidence:** Specific files, code paths, configurations affected
- **Findings:** Issues discovered (organized by severity: Critical, High, Medium, Low)
- **Proposal:** What should change, and why
- **Remediation effort:** Estimated hours to fix
- **Status:** Open, in-progress, resolved, or deferred

### Report Types

| Type | Generated by | When | Read-only? |
|---|---|---|---|
| **Code Review** | `code-reviewer` agent | Before PR merge | Yes (findings only) |
| **Security Audit** | `security-auditor` agent | After implementation (stage 3) | Yes (findings only) |
| **Design Critique** | `design-reviewer` agent | During architecture phase | Yes (findings only) |
| **Vulnerability Assessment** | `vulnerability-analyst` agent | On-demand or scheduled | Yes (findings only) |
| **Performance Analysis** | `performance-engineer` agent | Before load testing | Yes (findings only) |
| **Threat Model** | `threat-analyst` agent | During architecture phase | Yes (findings only) |

## Verification Procedures

### Write-Attempt Test

Evidence that the execution boundary holds (read-only core):
- Timestamp when test was run
- Agent attempting write operation
- Permission refusal captured
- Trace ID for investigation

### Session Trace Export

Telemetry and observability exports:
- OTLP traces from agent execution
- Cost and latency metrics
- Model token usage (input/output)
- Tool invocations and results

### Pre-Change Baseline

Before making significant changes, capture:
- Current performance metrics (API latency, memory, throughput)
- Test coverage percentages
- Build time and artifact size
- Deployment duration

### Post-Change Comparison

After changes, verify:
- No performance regression (latency within 5% of baseline)
- Coverage did not decrease
- Build time acceptable
- No new warnings or deprecations

## Sourcing

All audit artifacts in this folder are **read-only evidence** — they originate from:
- **Agent findings** (code-reviewer, security-auditor, design-reviewer, vulnerability-analyst)
- **CI/CD execution logs** (build outputs, test results, deploy logs)
- **Manual verification procedures** (write-attempt test, lab exercises, performance testing)
- **Observability exports** (telemetry, metrics, logs, traces)

## Access & Retention

### Access
- **Dev lead:** Views all audits to track system health
- **Tech lead:** Reviews security and performance findings before production deployment
- **Architects:** Review design critiques and threat models
- **On-call team:** Views incident analysis and related ADRs for context

### Retention Policy
- **Security findings:** Keep indefinitely (regulatory requirement)
- **Code review findings:** Keep for 12 months (trend analysis)
- **Performance reports:** Keep for 6 months (regression detection)
- **Incident analysis:** Keep indefinitely
- **Sensitive data:** Redact customer records, PII, and secrets before archival

## When to File Here

Add an audit artifact when:
1. Running agent-assisted reviews:
   - After `/security-scan` — file the security-auditor findings
   - After `/code-review` — file the code-reviewer findings
   - After design critique — file the design-reviewer findings

2. Capturing evidence:
   - After running write-attempt test (D4 §8 requirement)
   - After session trace export (for cost analysis or investigation)
   - After performance baseline or regression test

3. After production incidents:
   - Document root cause analysis
   - Link to related ADR or capability
   - Post-incident action items and prevention measures

4. Before major deployments:
   - Capture pre-deployment baseline
   - Run security and performance scans
   - Get sign-offs from required reviewers

## Critical Findings Escalation

### Critical Severity

**Examples:**
- SQL injection vulnerability (CVSS 9.0+)
- Hardcoded database password or API key
- Unpatched dependency with active CVE
- Authentication bypass
- Privilege escalation

**Action required:** Stop all work, escalate to security team, fix before production deployment.

### High Severity

**Examples:**
- Missing input validation on user-facing endpoints
- Unencrypted transmission of sensitive data
- Missing rate limiting on APIs
- Performance degradation > 20%
- Test coverage dropped below 75%

**Action required:** Create ticket, include in next sprint, document remediation plan.

### Medium Severity

**Examples:**
- Code style violations (refactoring debt)
- Missing documentation
- Inefficient database queries (sub-optimal but acceptable)
- Deferred dependency updates

**Action required:** Include in backlog, document as known limitation if deferred.

### Low Severity

**Examples:**
- Typos in comments or documentation
- Unused variables
- Minor performance optimizations (negligible impact)
- Deprecation warnings (non-blocking)

**Action required:** Include in code review feedback, not a blocker for merge.

## Reviewing Audit Reports

### As a Developer

**When you see audit findings:**
1. Review the evidence (specific code references)
2. Understand the consequence (why is this a problem?)
3. Implement the fix or create a ticket
4. Request re-scan if automated auditor exists
5. Document the decision if deferred

### As a Tech Lead

**Before signing off on a deployment:**
1. Review all Critical findings (must be zero before production)
2. Review High findings and remediation timelines
3. Verify security team sign-off (if auth/data/API changes)
4. Spot-check compliance with architecture ADRs
5. Approve or request changes

### As a Security Team Member

**During security audit phase:**
1. Review automated scanner findings
2. Spot-check for false positives (request agent to re-examine)
3. Identify patterns (e.g., repeated authentication bypass attempts)
4. Update security guidelines based on findings
5. Approve remediation plans or escalate to CISO

## Incident Post-Mortems

When a production incident occurs:

1. **Document the incident:**
   - What was the impact (downtime, data loss, customer-facing effect)?
   - When did it start and end (duration)?
   - Root cause analysis (technical, operational, process failure)?

2. **Create a post-mortem artifact:**
   - File as `incident-analysis_<system>_<date>.md`
   - Include timeline of events
   - Root cause (link to related ADR or design flaw)
   - Prevention measures (code, process, monitoring)

3. **Track action items:**
   - Link to related ADR (create one if architectural issue)
   - Create tickets for prevention measures
   - Assign ownership and target dates

4. **Share and follow up:**
   - Review with team
   - Update runbooks and alerts
   - Add preventive tests to test suite
