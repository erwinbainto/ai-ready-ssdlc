The chain

D4 is the harness deliverable. Everything else is either an input to it or evidence of it. The reference architecture is the design; the forms capture the decisions; the artefacts are D4 in deployable form; the deck reports what was built.

Step by step

  1. Read the reference architecture deck. You are producing the delivery instance of it. The tiers, primitives and plateau notation on the D4 deck all come from here.
  2. Fill the enterprise form once. Start with section 0 — the seven decisions that gate everything. Two of them, KPI freeze memory tiers, must be agreed in writing with RRD or you stop.
  3. Run each GENERATE step in the enterprise form to produce the enterprise/ artefacts, then publish them as a plugin. Record the version.
  4. Fill the application form five times, one per app, each citing the enterprise version. The knowledge connection (.claude/context/) is drafted by the explorer agent and corrected by the Dev Lead — it cannot be templated.
  5. Run the write-attempt test per app. Attempt an edit; capture the refusal and the trace reference. This is the single row that proves read-only rather than asserting it.
  6. Verify with the routine: /status, /context, /mcp, /agents, /skills, /hooks, /doctor, /usage.
  7. Generate the brief. Run the script over the six filled forms.
  8. Hand the brief to Claude with: “build the D4 harness deck from this brief.” The deck comes back in the reference-architecture style.

Running the generator

Once all six forms are filled:

python3 genbrief.py \
  --enterprise D4_Enterprise_Harness_Form.md \
  --apps app1.md app2.md app3.md app4.md app5.md \
  --out D4_Harness_Deck_Brief.md

The parser tolerates hand formatting and reads values from the tables by section. Any field left as <...> is carried through as NOT PROVIDED, so an incomplete form still produces a usable brief that shows exactly what is missing rather than failing.

What the brief contains. A slide plan mapped to specific reference-architecture slides, the resolved enterprise values, a resolved block per application, a per-application status table with a derived Full Reduced Substituted profile, and a consolidated open-items list. Claude turns that into the deck.

What actually satisfies D4

Filling the forms is not the deliverable. Three things have to be true:

1. The artefacts exist and are deployed. A location written in a form is a pointer, not a file. The GENERATE steps have to be run and the config committed.

2. The boundary is demonstrated, not asserted. The write-attempt test, with a trace reference, is the proof. Without it, “read-only” is a claim.

3. It is showcased live. D4 is showcased in system and Claude artefacts. RRD sees the harness answer a real question against their code, a server return a real result, and a write be refused. The forms and records are the supporting evidence, not the deliverable itself.

Two stop conditions. A Substituted profile on the execution boundary means read-only is not enforced — nothing runs. A Substituted profile on assurance means nothing that runs can be evidenced — no D10. Everything else has a reduced implementation you can deploy now and record honestly with a compensating control.
Version caution. Claude Code keys and behaviour change between releases. Before relying on any generated file, run claude plugin validate and /doctor, and confirm /status, /mcp and /hooks show what you expect. There are field reports of file-read deny rules being ignored, so the read-only boundary is held by the PreToolUse hook as well as the deny list — never the deny list alone.
